## 0. 一言でいうと

公開済みの「英検2級 英単語特訓」（SwiftUI / SwiftData / 完全オフライン / 買い切りIAP）を
ベースに、**単語 → 4択問題** に主データを差し替えた ITパスポート試験の特訓アプリを作る。

- **流用する**: アプリ骨格、間隔反復（Leitner方式）、4択クイズの進行、学習履歴グラフ、
  課金・試用の仕組み、シード投入の堅牢性設計、CI（GitHub Actions / XcodeGen）
- **作り替える**: データモデル（単語→問題）、クイズの解答後フロー（**解説表示ステップを追加**）、
  問題一覧画面、分野・シラバス分類
- **削除する**: タイピング機能一式、スペルチェック、TTS聞き流し、ユーザー自作単語

問題データは同梱JSONとして持ち、AIによる作問（§9のプロンプト）で生成 → 人手レビュー → シード化する。

## 4. データモデル（SwiftData）

ベース同様、マスター（Read-Only）と進捗（Read-Write）を **ID文字列でのみ疎結合** にする。
`@Relationship` は張らない（マスター総入れ替え時に進捗へカスケードさせないため。
理由の詳細はベース `WordMaster.swift` 冒頭コメント参照）。

### 4.1 QuestionMaster（問題マスター）

```swift
@Model
final class QuestionMaster {
    /// 例: "ITP_SEC_0042"。公開後は絶対に改名しない（§8.3）
    @Attribute(.unique) var questionId: String

    var questionText: String          // 問題文
    var choiceA: String
    var choiceB: String
    var choiceC: String
    var choiceD: String
    var correctChoiceRaw: String      // "A"〜"D"（シード上の正解。表示時はシャッフル §6.2）

    var explanation: String           // 正解の解説（なぜ正しいか）
    var explanationA: String          // 各選択肢の解説。正解の選択肢には
    var explanationB: String          //   「正解。〜」、誤答には「不正解。〜（用語の意味）」
    var explanationC: String          //   を入れる（§9の作問条件4に対応）
    var explanationD: String

    var fieldRaw: String              // 分野: "strategy" | "management" | "technology"（§7）
    var midCategoryRaw: String        // 中分類コード（§7の表）
    var keywords: [String]            // 主題キーワード（"ゼロトラスト" 等。検索と重複チェックに使用）

    var syllabusVersion: String       // 準拠シラバス（例: "6.3"）
    var difficultyRaw: Int            // 1:基礎 / 2:標準 / 3:応用（§10のtierを兼ねる）
    var updatedAt: Date
}
```

- 選択肢の解説を4本の独立フィールドで持つのは、解説画面（§6.3）で
  「選んだ選択肢の解説を強調表示」するため。1本のテキストに混ぜると分解できない。
- 頻出度ランク（ベースのA/B/C）は持たない。過去問統計を持たないため根拠がない。
  代わりに `difficultyRaw` を出題階層と課金境界に使う。

### 4.2 UserProgress（進捗。ベースからリネームのみ）

```swift
@Model
final class UserProgress {
    @Attribute(.unique) var questionId: String
    var lastReviewedAt: Date?
    var correctCount: Int
    var attemptCount: Int
    var reviewBox: Int = 0        // Leitnerボックス。正解で+1、不正解で0
    var nextReviewAt: Date?
    // record(isCorrect:) / status(at:) / markForReview / markAsMemorized は
    // ベースの実装をそのまま使う（間隔テーブル 0/1/3/7/14/30日、masteredBox=3）
}
```

習熟段階（未学習/要復習/学習中/習得済み）は保存せず `reviewBox` から導出する
（ベース `LearningStatus` の設計と同じ。表示名は「覚えた」→「習得済み」に変更）。

「習得済み = 7日間隔の復習に正解」という基準は問題演習でもそのまま妥当:
1回解けただけの問題は本番では解けないことが多く、間隔をあけて再度正解できて初めて定着とみなす。

### 4.3 StudyLog（日次履歴。流用）

ベースのまま。`masteredBreakdown` のキーを「分野×難易度」に変更する
（ベースは「階層×ドメイン」。`MasteryBreakdown` のキー生成部のみ修正）。

## 5. 主要機能仕様

### 5.1 出題順（StudyQueue — ベース流用）

優先度は変更しない:

1. 復習期限が来ている問題（間違えた問題・間隔満了）
2. 未出題の問題
3. 期限前の問題（期限が近い順）

同一優先度内はシャッフル。ベースの `StudyQueue.prioritize / dueWords / dueCount` を
型名だけ変えて使う。純粋関数なのでユニットテストも流用する。

### 5.2 出題範囲（StudyScope）

ユーザーが選べる軸:

- **分野**: 全分野ミックス（既定）/ ストラテジ系 / マネジメント系 / テクノロジ系
- **難易度**: 既定 = 全難易度（権利の範囲内）。設定で基礎のみ等に絞れる

出題母集団は **ユーザー設定 × 課金権利の積** で決める（ベース `fetchStudyPool` の設計。
出題されない理由が「設定」か「未購入」かを画面で出し分けるため、2つを混ぜない）。

分野ミックス時は本試験の比率（ストラテジ35 : マネジメント20 : テクノロジ45）に
厳密に合わせる必要はない。SRSの復習期限が優先順位を支配するため、比率は
シードデータの問題数比で自然に反映させる（§8.2）。

### 5.3 問題一覧

ベースの WordList を改修:

- 絞り込み: 分野 / 中分類 / 習熟度（未学習・要復習・学習中・習得済み）/ 難易度
- 検索: 問題文とキーワード（`keywords`）に対する部分一致
- 詳細画面: 問題文・4選択肢・正解・**全選択肢の解説**を表示。
  「この問題をやり直す」（reviewBox=0に戻す）と「習得済みにする」操作を置く
- 一覧・詳細は課金状態に関係なく全問閲覧できる（ベースの方針を踏襲:
  出題対象から外れるだけで、閲覧まで止めない。§10）

### 5.4 ホーム

- 「復習期限の来ている問題が N 問」→ タップで復習のみ演習を開始（`QuizScope.reviewOnly` 流用）
- 分野別習熟度バー（3分野それぞれの 習得済み/全問数）。**合格基準が分野別にあるため、
  ここは英単語版の「階層別」より重要**。弱点分野が一目で分かることを最優先にする
- 連続学習日数・直近1週間ミニグラフ（ベース流用。当日未学習でも前日までで数える等の
  仕様は `StudyHistory.swift` のまま）

## 6. 演習（クイズ）仕様 — ベースとの最大の差分

ベースのクイズは「単語→4択の意味→正誤が出たら即次へ」だが、本アプリは
**解説を読むことが学習の本体**。フローを次のように変える。

### 6.1 進行フロー

```
スタート画面（出題範囲・問題数の確認）
  → 出題（問題文 + 選択肢4つ）
  → 解答タップ
  → 正誤表示 + 解説パネル（§6.3）     ← 追加ステップ
  → 「次の問題へ」ボタン
  → …（10問で1セット）
  → 結果画面
```

- 1セット **10問**（ベースは15問。解説を読む分1問あたりの時間が長いため減らす。
  定数 `questionCount` を変えるだけ）
- **制限時間は設けない**（ベースの10秒/問タイマーは撤去）。解説を読み込む学習体験と
  時間プレッシャーは両立しない。タイマー関連コード（`remainingSeconds` / `timeoutCount` /
  `suspendTimer` 等）は削除してよい。ただしバックグラウンド移行時の途中保存
  （`progressRepository.save()`）は残すこと
- 進捗記録は解答タップ時に `UserProgress.record(isCorrect:)`（ベース同様）。
  保存はセット区切りでまとめて行う（1問ごとに save しない — ベースのコメント参照）

### 6.2 選択肢の表示順

シードデータは正解を `correctChoice: "A"` のように持つが、**表示時に毎回シャッフル**する。
固定順だと「この問題の答えは3番目」という位置記憶で解けてしまい、SRSの意味がなくなる。

実装はベースの `buildQuestion` と同じ方式: シャッフル後の正解位置を
`QuizQuestion.correctIndex` として挿入時に確定させる（文字列検索で正解を探さない）。
ベースにあった「ダミー選択肢の動的生成」「意味の重複除外」は不要になる
（選択肢は問題データに固定で入っているため）。

### 6.3 解説パネル

解答直後に表示する内容:

1. 正誤バッジ（正解/不正解）と正解の選択肢
2. **選んだ選択肢の解説を最上部に強調表示**（不正解時: なぜそれが違うか）
3. 正解の解説
4. 残りの選択肢の解説（折りたたみ展開可）
5. メタ情報: 分野・中分類・キーワード

「次の問題へ」は解説パネルの下に置き、誤タップで解説を飛ばさないよう
解答ボタンと同じ位置に出さない。

### 6.4 結果画面

ベースの `QuizResultView` を流用しつつ:

- 正答数 / セット数、今回新たに「習得済み」になった問題数（`newlyMemorizedCount` 流用）
- **分野別の正誤内訳**を追加（今回のセット内）
- 間違えた問題のリスト → タップで解説を再表示、「間違えた問題だけやり直す」ボタン

## 8. 問題データ（シードJSON）仕様

### 8.1 ファイルと形式

`Resources/question_master_seed.json`（ベースの `word_master_seed.json` と同じ位置づけ）。

```jsonc
{
  "version": 1,                    // 上げるとアプリ更新時にUpsertが走る
  "syllabusVersion": "6.3",
  "questions": [
    {
      "questionId": "ITP_SEC_0042",
      "questionText": "ゼロトラストの考え方に基づくセキュリティ対策の説明として、最も適切なものはどれか。",
      "choices": {
        "A": "社内ネットワークからのアクセスは常に信頼し、社外からのアクセスだけを検証する。",
        "B": "アクセスのたびに利用者や端末を検証し、社内外を問わず暗黙には信頼しない。",
        "C": "一度認証に成功した端末には、以後すべてのシステムへのアクセスを許可する。",
        "D": "ファイアウォールを設置し、境界の内側では自由な通信を許可する。"
      },
      "correctChoice": "B",
      "explanation": "ゼロトラストは「何も信頼しない」を前提に、アクセスごとに利用者・端末・状況を検証する考え方である。",
      "choiceExplanations": {
        "A": "不正解。社内を無条件に信頼するのは従来の境界型防御の考え方であり、ゼロトラストの否定する前提である。",
        "B": "正解。ゼロトラストでは社内外を区別せず、すべてのアクセスを検証する。",
        "C": "不正解。一度の認証で永続的に信頼する方式は、端末の乗っ取りに対して無防備になる。",
        "D": "不正解。境界型防御（ペリメタセキュリティ）の説明であり、ゼロトラストとは逆の発想である。"
      },
      "field": "technology",
      "midCategory": "SEC",
      "keywords": ["ゼロトラスト", "境界型防御"],
      "difficulty": 2
    }
  ]
}
```

省略可能な項目:

- `keywords` — 既定は空配列
- `difficulty` — 既定は 2（標準）
- `syllabusVersion` — 問題ごとに書けばファイル全体の値を上書きする。
  改訂時に一部の問題だけ差し替える運用のため

`updatedAt` は持たせない。`QuestionMaster.updatedAt` は Upsert 時に現在時刻で埋める
（シードに手で書かせると、更新したのに書き換え忘れた項目が生まれる）。

### 8.2 問題数の目標

| フェーズ | 総問題数 | 内訳の目安 |
| --- | --- | --- |
| リリース最低ライン | 300問 | ストラテジ105 / マネジメント60 / テクノロジ135（本試験比率 35:20:45） |
| 目標 | 800〜1,000問 | 同比率。各中分類最低10問 |

難易度の比率目安: 基礎(1) 30% / 標準(2) 50% / 応用(3) 20%。
標準(2)が本試験の中心レベル。応用(3)は最新シラバス項目・計算問題・複合知識を含む。

### 8.3 questionId の体系（不変条件）

```
ITP_<中分類コード>_<4桁連番>   例: ITP_SEC_0042
```

- **公開後の改名・削除は原則禁止**。改名は「削除+新規」となり、その問題の学習履歴が
  全ユーザーで失われる（ベース `series-architecture.md` §2 と同じ理屈）
- 問題文・選択肢・解説の**修正は自由**（IDが同じなら履歴は保持される）
- 明白な誤りで出題を止めたい問題は、削除ではなくシードから外す
  （Seederは孤児進捗を許容する設計 — ベースの挙動そのまま）

### 8.4 シード投入（ベースの堅牢性設計を必ず維持）

`WordMasterSeeder` → `QuestionMasterSeeder` に改名して流用。次の設計判断は
ベースのREADMEに理由込みで書かれており、**維持必須**:

- seed `version` が既適用より新しいときだけUpsert。ただし `QuestionMaster` が0件なら
  バージョンに関わらず再シード
- バージョンの記録は `context.save()` 成功**後**（逆にすると失敗時に復旧不能）
- シード失敗でも起動は継続（ログのみ）
- 永続ストアが開けなければインメモリにフォールバック

## 9. AI作問ワークフロー

問題データはAI（Claude等）で下書きを生成し、**人手レビューを経て**シードに取り込む。
レビューなしで同梱しないこと（国家試験対策アプリで誤答解説が間違っていると致命的）。

### 9.1 作問プロンプト

`docs/question-authoring-prompt.md` に完全版を置く（本リポジトリに同梱済み）。
骨子は以下で、依頼者指定の作問条件をそのまま核にしている:

> あなたは国家試験「ITパスポート試験」の専門作問者です。
> 最新のシラバス（出題基準）に厳密に準拠した4択問題を生成してください。
>
> 1. 分野: 指定された分野（ストラテジ系 / マネジメント系 / テクノロジ系 / 全体ランダム）からバランスよく出題
> 2. レベル: ITパスポート本試験と同等の難易度（初学者〜実務入門レベル）
> 3. 形式: 4択（選択肢: A, B, C, D）
> 4. 解説: 正解の理由だけでなく、すべての誤答選択肢（なぜ不正解か・その用語の意味）を明記すること
> 5. 最新キーワード（生成AI、DX、ゼロトラスト、アジャイル開発、最新法規など）も積極的に含めること

これに **§8.1のJSONスキーマでの出力指定** と中分類コード表を足したものが実際のプロンプトになる。

### 9.2 生成の運用

- 中分類単位でバッチ生成する（例: 「SEC で標準難易度を20問」）。分野全体で一括生成すると
  中分類の偏りが検出しにくい
- `questionId` はAIに振らせない。レビュー通過後にスクリプトで連番採番する
- 既存問題の `keywords` 一覧をプロンプトに添え、**同一論点の重複出題を避けさせる**

### 9.3 レビューチェックリスト（1問ごと）

- [ ] 正解が一意に定まる（複数正解・解釈割れがない）
- [ ] 誤答選択肢が「明らかに変」ではなく、もっともらしい（実在用語の説明になっている）
- [ ] 4つの解説すべてが事実として正しい
- [ ] シラバスの用語例に載っている表記を使っている（例: 「サブスクリプション」等の表記ゆれ）
- [ ] 計算問題は検算済み
- [ ] 法規問題は現行法に一致（改正が速い領域。`syllabusVersion` と `updatedAt` を必ず入れる）

### 9.4 機械検証（シードビルド時にスクリプトで落とす）

- questionId の重複・形式違反（`ITP_<既知の中分類コード>_\d{4}`）
- `correctChoice` が A〜D / `choiceExplanations` が4キー揃っている
- 正解選択肢の解説が「正解」、誤答の解説が「不正解」で始まる
- 同一 `questionText` の重複
- field と midCategory の対応が§7の表と一致

## 10. 課金・試用

ベースの3層構造（`AccessRights` / `TrialManager` / `Entitlements`）をそのまま流用し、
語彙階層（tier）の代わりに **難易度（difficulty）** を課金境界にする。

| difficulty | 内容 | 無料/課金 |
| --- | --- | --- |
| 1（基礎） | 用語の定義レベル | 無料 |
| 2（標準） | 本試験の中心レベル | 無料 |
| 3（応用） | 最新シラバス項目・計算・複合問題 | **試用14日 → 買い切りIAPで解放** |

- 試用期間14日はベースの `TrialManager` のまま（時計巻き戻し対策込み）
- 試用終了後も**アプリの機能は一切止めない**。応用問題が出題対象から外れるだけで、
  問題一覧での閲覧・解説の読み直しは常に全問できる（ベースのApp Review対策方針を踏襲）
- プロダクトID: `com.eitango.itpassport.unlock.advanced`（非消耗型1つ。bundle IDに合わせて確定させる）
- `Transaction.updates` の購読による払い戻し反映もベースのまま

> 代替案として「模擬試験モードを課金対象にする」も検討したが、Phase 1に模試がない（§14）ため
> 難易度境界を採用。模試実装後に商品を追加する場合は非消耗型を分けず、同じ解放に含める
> （商品を増やすと復元・訴求が複雑になる）。

## 11. 模擬試験モード（Phase 2）

本試験形式の通し演習。Phase 1 には含めないが、データモデルは対応済みにしておく
（追加フィールド不要。出題時に分野比率でサンプリングするだけ）。

- 92問（採点対象問題数に合わせる）/ 制限時間120分（全体タイマー。1問ごとではない）
- 分野比率: ストラテジ32 / マネジメント18 / テクノロジ42（92問時の比率換算）
- 演習と違い**解答直後に解説を出さない**。全問解答→採点→結果画面から各問の解説へ
- 採点は素点比例の目安表示とし「推定スコア」と明記する（実試験はIRT方式のため正確な再現は不可能。
  断定表示すると誤解を招く）
- 中断・再開に対応（120分を一度に取れないユーザーが多い）
- 模試の解答も `UserProgress` に記録する（SRSに反映）

## 12. 非機能要件

| 項目 | 内容 |
| --- | --- |
| オフライン | サーバー通信なし。アカウントなし。ベースと同じプライバシーマニフェスト構成（`PrivacyInfo.xcprivacy`、UserDefaultsのRequired Reason API宣言） |
| 起動堅牢性 | §8.4。シード失敗・ストア破損でも起動する |
| パフォーマンス | 1,000問規模で問題ないことを確認。出題プールのフェッチはセット開始時に1回（ベースの方針） |
| アクセシビリティ | Dynamic Type対応。問題文・解説は長文になるためスクロール前提のレイアウト |
| 文字量 | 問題文は最大300字、選択肢は各最大120字を目安にレイアウトを設計（本試験の実問題に準拠した分量） |

## 13. テスト方針

ベースのテスト構成を踏襲。**SRS・出題順・履歴集計・課金判定はUIに現れず静かに壊れる**ため、
ユニットテストを必須とする（ベースのテストがほぼそのまま流用できる）。

| テスト | 内容 |
| --- | --- |
| `SpacedRepetitionTests` | Leitner間隔・status導出・日付丸め・上限・手動での状態変更 |
| `StudyQueueTests` | 出題優先度、復習のみの抽出、解き直しの順序保持 |
| `StudyHistoryTests` | 0埋め・期間前からの習熟度引き継ぎ・連続日数・重み付き正答率・週まとめ |
| `EntitlementTests` | 難易度による課金境界、試用期間、時計巻き戻し対策 |
| `StudyScopeTests` | 出題範囲と権利の積、分野変更時の中分類クリア、リポジトリ経由のプール |
| `MasteryBreakdownTests` | 内訳キーの形式、分野・難易度での集計、孤児進捗の除外、増分更新 |
| `QuizFlowTests` | 選択肢シャッフルの正解位置維持、解説ステップを含む進行、分野別集計、0問時の挙動 |
| `SeedValidationTests` | §9.4の機械検証をテストとしても実行（同梱シードに対して） |
| UIテスト | ホーム・演習（解説パネル含む）・問題一覧・詳細・履歴・購入画面のスクリーンショットをCIで撮影 |

シードの検証は `scripts/validate_seed.py`（CIのUbuntuジョブ）と `SeedValidationTests`（Xcode）の
二重になっている。CIでスクリプトを回すだけだと手元でシードを編集したときに気付けず、
テストだけだと形式ミスのために高価なmacOSランナーを消費することになるため、両方に置く。
